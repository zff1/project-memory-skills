# Topic Save：保存话题记忆

把项目任务中有复用价值的经验，提炼成简洁的项目本地记忆。只保存能够帮助未来任务的知识；不要把记忆目录变成聊天记录 dump，也不要把未经审核的猜测写进去。

## 什么时候使用

完成有实际意义的项目任务后使用，尤其是以下情况：

- 实现或修改功能；
- 修复不明显的 Bug；
- 做出或调整架构决策；
- 发现项目约定或可复用的代码入口；
- 完成了后续会话需要继续的里程碑。

如果没有学到任何长期有效的知识，不要创建空的或形式化的记忆条目。如果任务属于尚未结束的连续工作，仍然可以保存简短的会话摘要。

## 记忆目录结构

只能写入以下项目本地目录结构：

```text
.project-memory/
├── project.md                    # 项目级上下文
├── index.json                    # 话题索引
└── topics/
    └── <topic-id>/
        ├── TOPIC.md              # 话题范围和代码入口
        ├── MEMORY.md             # 长期记忆
        └── sessions/
            └── <timestamp>-<short-description>.md  # 会话摘要
```

绝对不要把秘密或凭证写入任何记忆文件，包括 API Key、访问 Token、Cookie、私钥、密码或未经脱敏的个人数据。

## 什么内容值得长期保存

优先保存以下类别：

- **Decision（决策）**：已确认的设计或实现选择，以及做出选择的原因；
- **Constraint（约束）**：未来工作必须遵守的规则；
- **Pitfall（踩坑）**：可复现的失败模式及其规避方式；
- **Reference（引用）**：重要文件、符号、命令或代码入口；
- **Convention（约定）**：稳定的项目风格或工作方式；
- **Dependency（依赖）**：未来修改必须保持的跨模块关系；
- **Open question（待确认问题）**：尚未解决、不能当作事实陈述的事项。

不要保存：

- 原始聊天记录；
- “修改了一个按钮”这类普通进度；
- 未验证的模型猜测；
- 临时调试输出或一次性变量；
- 没有增加信息的重复条目；
- 秘密和敏感数据。

## 执行步骤

1. 确定当前任务涉及的 topic。优先使用 `.project-memory/index.json` 中已有的 topic ID；只有在这个领域很可能反复出现时才创建新 topic。
2. 检查任务结果、相关代码、测试结果以及最终 diff（如果有）。在当前代码、测试输出或用户明确决策支持之前，把所有说法都当作候选内容。
3. 只提炼长期有效的事实。每条候选记忆都记录类别、简洁内容、状态（`verified`、`user-confirmed` 或 `open`）、证据路径或命令，以及日期。
4. 与现有 `MEMORY.md` 对比：
   - 合并等价事实；
   - 更新过时事实，不要追加重复内容；
   - 如果需要保留历史，把被替代的决策标记为已废弃；
   - 遇到矛盾时不要静默选择其中一条。
5. 对普通且低风险的新增内容，可以直接小范围更新相关 `MEMORY.md`。涉及架构、安全、数据、API、生产环境或其他高影响变化时，先展示拟保存的变更，并在用户确认后写入。
6. 当任务包含有价值的历史、未完成工作、有意义的决策或非显而易见的修复时，在 `sessions/` 下保存简洁的会话记录。会话记录应包含日期、目标、结果、修改文件、验证方式、决策和后续事项，不要保存完整对话。
7. 只有在创建、重命名或实质性修改 topic，或者需要修正关键词时，才更新 `index.json`。索引只保存路由元数据，不要把它变成第二份记忆文件。
8. 如果记忆和当前代码不一致，以当前已验证的证据为准，记录差异，并更新或标记过时条目，不要让两条互相矛盾的内容同时保持有效。
9. 写入后检查 diff 并校验 JSON。没有确认目标文件确实成功修改前，不要声称记忆已经保存。

## 推荐的记忆条目格式

保持 `MEMORY.md` 可读，并按类别组织：

```markdown
# 鉴权记忆

## 已确认的决策

### Token 刷新统一放在请求层

- 状态：verified
- 详情：组件不能自行刷新或附加 Token。
- 证据：`src/services/http.ts`、`npm test -- authentication`
- 更新时间：2026-08-05

## 约束

- 凭证过期时必须返回可区分的鉴权错误。

## 已知踩坑

- 并发请求必须共享同一次刷新操作，否则请求之间可能互相使 Token 失效。

## 代码引用

- 请求层：`src/services/http.ts`
- 鉴权状态：`src/stores/auth.ts`

## 待确认问题

- 确认是否需要支持多账号会话。
```

使用宿主环境提供的真实当前日期。不要伪造证据、测试结果或源代码路径。

## 创建 topic

创建 topic 时：

1. 在 `index.json` 中添加稳定条目，包含 `id`、`name`、`keywords`、`path`、`status` 和 `updated_at`。
2. 创建 `TOPIC.md`，描述话题范围、不包含的内容、相关代码和依赖。
3. 创建聚焦的 `MEMORY.md`，只记录当前任务学到的事实。
4. 只有需要会话记录时才创建 `sessions/`。

不要为每个工单、文件或对话都创建 topic。Topic 应代表会反复出现的业务领域或模块。

## 安全和冲突处理

如果候选内容会产生以下影响，写入前必须获得用户确认：

- 替换已有的架构、API、数据结构、安全规则或生产约束；
- 与当前有效的记忆条目矛盾；
- 包含未来实现可能依赖的未验证说法；
- 修改 `project.md` 中的项目级规则。

需要确认时，简洁展示旧条目、新条目、证据和受影响的 topic。如果用户拒绝，保留原有记忆，并可选择把该事项记录为待确认问题。

## 完成标准

只有满足以下条件，保存才算完成：

- 每条保存的事实都属于正确的 topic；
- 长期事实简洁且分类清晰；
- 在有帮助的地方记录了证据或状态；
- 重复、过时和冲突条目都得到明确处理；
- 没有写入秘密或原始聊天记录；
- 相关会话历史已归档，但没有让 `MEMORY.md` 变得臃肿；
- JSON 和 Markdown 文件仍然有效；
- 已检查最终 diff，并准确报告实际变化。
